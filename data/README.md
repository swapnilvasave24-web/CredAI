# CredAI Dataset Documentation

## Honesty Notice (read first)

This prototype was built in an offline sandbox with **no access to Kaggle**.
`scripts/download_data.py` is written to pull the real **Home Credit Default
Risk** dataset from Kaggle when you run it on a machine with internet + Kaggle
API credentials. Because that download could not be performed here, the
repository ships with `scripts/generate_homecredit_like_data.py`, which
generates a **synthetic dataset that mirrors the real Home Credit schema**
(same column names, same rough distributions/ranges as documented publicly by
Kaggle for `application_train.csv`, `bureau.csv`, `previous_application.csv`,
`installments_payments.csv`), so the entire pipeline (preprocessing, feature
engineering, XGBoost, SHAP, federated learning, fairness) runs end-to-end
exactly as it would on the real data.

**This is clearly labeled in the UI and in every generated report as
`"Data source: Synthetic (Home-Credit-schema) — replace with real Kaggle
download via scripts/download_data.py"`.** Nothing in this app claims the
demo model was trained on real Home Credit records, and nothing claims the
alternative-data (UPI/utility/savings) features are real transactions.

## 1. Real Dataset — Home Credit Default Risk

- **Source:** Kaggle competition ["Home Credit Default
  Risk"](https://www.kaggle.com/c/home-credit-default-risk)
- **License:** Kaggle competition data, for research/educational use per
  Kaggle's competition rules. Do not redistribute the raw files.
- **How to get it for real training:**
  1. Create a Kaggle account and accept the competition rules.
  2. Create an API token: Kaggle → Account → "Create New API Token" →
     downloads `kaggle.json`.
  3. Place it at `~/.kaggle/kaggle.json` (`chmod 600`).
  4. Run `python scripts/download_data.py` — this calls the Kaggle API and
     unzips the files into `data/raw/`.
  5. Run `python scripts/prepare_data.py` to regenerate
     `data/processed/applicant_dataset.csv` from the **real** files instead
     of the synthetic generator.

Files the pipeline expects in `data/raw/` once downloaded:
`application_train.csv`, `application_test.csv`, `bureau.csv`,
`bureau_balance.csv`, `previous_application.csv`, `POS_CASH_balance.csv`,
`credit_card_balance.csv`, `installments_payments.csv`,
`HomeCredit_columns_description.csv`.

## 2. Target Variable

- **Column:** `TARGET` (application_train.csv)
- **Meaning:** 1 = client had payment difficulties (late payment on at least
  one installment in the first N installments of the loan); 0 = all other
  cases.
- **Positive class (1):** higher credit/default risk.
- **Negative class (0):** lower credit/default risk.
- In the real competition data this is heavily imbalanced (~8% positive).
  The synthetic generator reproduces this imbalance (~configurable, default
  ~9%).

`TARGET` is **not** "the applicant is a bad person" and is **not** an
official regulatory default definition — it is Kaggle's competition-defined
proxy for repayment difficulty. CredAI's "default probability" is the
model's calibrated estimate of this proxy, not a legal determination.

## 3. Derived Features (from real-schema tables)

Aggregated at applicant level, respecting the train boundary (aggregations
computed independently per split, no test-set statistics leaked into train):

- `bureau.csv` → number of previous credit bureau loans, total/average
  credit sum, overdue amounts, active-loan ratio.
- `previous_application.csv` → count of previous applications, approval
  rate, average previous credit amount.
- `installments_payments.csv` → average days-late on installments,
  proportion of late installments, payment-to-installment ratio.
- `POS_CASH_balance.csv` / `credit_card_balance.csv` → average utilization,
  DPD (days-past-due) indicators.
- Core `application_*` fields → income, credit amount, annuity,
  employment duration (`DAYS_EMPLOYED`), age (`DAYS_BIRTH`), family status,
  education, housing type.
- Engineered ratios: `DEBT_TO_INCOME = AMT_CREDIT / AMT_INCOME_TOTAL`,
  `ANNUITY_TO_INCOME = AMT_ANNUITY / AMT_INCOME_TOTAL`,
  `CREDIT_TERM = AMT_CREDIT / AMT_ANNUITY`, `EMPLOYED_TO_AGE_RATIO`.

## 4. Synthetic Alternative-Data Layer (clearly labeled `is_synthetic=true`)

Home Credit does **not** contain UPI transactions, Indian utility-bill
records, or e-commerce data. These columns are generated by
`scripts/generate_synthetic_data.py` and are **always prefixed / flagged**
so the API and UI can render a "Synthetic Prototype Data" badge next to
them:

| Column | Description | Generation logic |
|---|---|---|
| `syn_upi_txn_count_monthly` | Avg monthly UPI-style transactions | Poisson, λ scaled with income decile |
| `syn_avg_txn_amount` | Avg transaction size | Log-normal, mean scaled with income |
| `syn_txn_consistency` | 0–1 regularity score of transaction timing | Beta distribution, mean shifted up for stable-employment applicants |
| `syn_utility_payment_reliability` | 0–1 on-time utility payment rate | Beta distribution, negatively correlated with real `installments` late-payment rate (models a plausible real-world correlation) |
| `syn_monthly_savings_rate` | Fraction of income saved/month | Normal, mean scaled with income, floored at 0 |
| `syn_income_stability_score` | 0–1 stability of income | Derived from real `DAYS_EMPLOYED` + noise |

**Important:** these synthetic features are generated with a fixed seed
(`SEED=42`) from *already-existing* real-schema fields (income, employment
duration, existing late-payment rate) so they have a *plausible statistical
relationship* to the applicant rather than being pure noise — but they are
**not derived from `TARGET`**, so they do not leak the label. They exist to
demonstrate how an alternative-data layer would be integrated, not to
represent real behavior.

## 5. Federated Partitioning

`scripts/create_federated_clients.py` splits the applicant-level dataset
into three **non-IID** partitions to simulate three different institutions
with different customer bases:

- **Bank A** — biased toward salaried/employed applicants, mid-to-high
  income tercile.
- **Bank B** — biased toward self-employed / working-contract applicants,
  broader income range.
- **FinTech C** — biased toward younger applicants (lower `DAYS_BIRTH`
  magnitude) and thinner bureau history (fewer `bureau.csv` records),
  modeling a "new-to-credit" lender base.

Partitioning is done by sampling with feature-conditioned probabilities
(not a uniform random split), then each client's data is held completely
locally — the FL server (see `backend/app/federated/`) only ever receives
serialized model **weights**, never rows of client data.

## 6. Splits

- Stratified 70/15/15 train/validation/test on `TARGET`.
- Test set is untouched during model selection/hyperparameter choices.
- Federated client partitions are carved from the training split only; the
  global test set is held out centrally for the centralized-vs-federated
  comparison.

## 7. Limitations

- Dataset here is synthetic-but-realistic, not the actual Kaggle data —
  swap in real data via `scripts/download_data.py` + `scripts/prepare_data.py`.
  All downstream code (preprocessing, model, SHAP, fairness, FL) is written
  against the same column schema either way, so no other code changes are
  required.
- Synthetic alternative-data features are prototype placeholders for a
  concept, not validated real-world signals.
- `TARGET` is a Kaggle-competition-defined repayment-difficulty proxy, not
  an official credit-bureau default definition.
